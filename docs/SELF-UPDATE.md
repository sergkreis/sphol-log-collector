# Explicit portable self-update design

Chosen implementation: the existing frozen executable is copied into a private random per-user staging directory and re-entered in a narrow helper mode. No PowerShell, shell scripts, remote commands, installer, elevation, service, scheduled checks or browser handoff. Update checks/downloads run only after the Update button. A second explicit restart confirmation is required. Capture/uploads must already be stopped, including local-only and v2 capture; pending queues are preserved. Source runs display their version but cannot replace Python.

The fixed public repository is `sergkreis/sphol-log-collector`. Stable `vMAJOR.MINOR.PATCH` releases must include `SPHOLLogCollector.exe` and `update-manifest.json` with schema 1, version, asset, size and SHA-256. Exact release tag, asset name, API asset size and manifest must agree. HTTPS requests have host allowlists, redirect limits, byte budgets, socket and wall-clock deadlines. SHA-256 detects corruption/manifest disagreement, NOT publisher authenticity: releases are currently unsigned; a compromised repository/GitHub can supply both malicious bytes and checksums. No claim of Authenticode/signature verification is made.

The helper verifies staged/current hashes and paths, opens a Windows process handle and checks its image before signalling ready, then waits for that exact process to exit (never kills by name/PID). The UI closes local recordings and both SQLite queues before exit. Replacement keeps a same-directory rollback executable, restores it on replacement/launch failure, and launches the exact target without inherited PyInstaller extraction state. Symlinks/reparse components, UNC paths, alternate streams and non-regular entries are rejected. These checks do not defend against a malicious process already running as the same Windows user or an administrator; per-user ACL inheritance is assumed. A running new executable is not proof of functional health: backup is retained for recovery, not silently removed. Crashes after successful launch require manual recovery from backup; no false automatic health/rollback claim.

## Release ordering / compatibility

1. Review this local commit; do not push or publish until approved.
2. Run Windows Actions source Tk AND frozen helper smoke against isolated temporary dummy fixtures, with no production logs/credentials/PCs. Linux tests do not establish Windows acceptance.
3. Choose/bump `collector.version.VERSION` before each release. Build from that exact source; generate the manifest from the final executable via `tools.make_update_manifest` and upload it alongside the EXE. Publish a stable matching tag only after native gates pass. Candidate Actions artifacts are not releases.
4. Existing old executables cannot gain a button remotely: the first updater-capable build needs the existing distribution mechanism once. Thereafter users stay in the app.
5. Keep schema-1 delivery functional and schema-2 opt-in DEFAULT OFF. Updating does not change consent, DPAPI keys or queue formats. Deploy and validate a compatible server before advertising/enabling v2. The production server is still legacy; this work does not deploy it.

## Limits / failure recovery

No automatic update during a fleet. Stop capture/recording and wait for in-flight requests before updating. Portable EXEs in non-writable directories fail without asking for administrator rights. A timeout before the original process exits leaves it untouched. Downloads never touch queues/credentials/local session folders. Interrupted staging may leave bounded individual temporary downloads; no unattended cleanup traverses user directories. After replacement the `.rollback.exe` file in the original directory is retained; do not delete it before validating the new build. Each staging generation gets a distinct backup name; existing entries cause refusal rather than overwrite. Network/validation errors keep the collector open. Release availability and Windows native results must be reported separately from local source tests.
